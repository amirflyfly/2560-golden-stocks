# 2560 Strategy 产品 PRD

## 1. 产品定位

2560 Strategy 是面向 A 股短线策略研究和复盘的投研工作台。产品核心不是做通用行情终端，也不是直接替代券商交易软件，而是围绕“策略发现、候选解释、选股跟踪、回测验证、复盘沉淀、报表归因”形成一套可持续迭代的研究闭环。

第一阶段聚焦 2560 战法和首板涨停策略，后续扩展为多策略、多租户、可审计、可运维的轻量量化投研平台。

## 2. 产品目标

### 2.1 业务目标

- 将每日候选标的从“脚本结果”升级为“可解释、可跟踪、可复盘”的策略资产。
- 让用户在一个工作台内完成扫描、入池、看 K 线、回测、复盘和报表查看。
- 降低 mock/fallback 行情误用风险，把数据质量作为投研决策前置条件。
- 建立策略表现沉淀机制，为后续参数优化、策略淘汰和组合管理提供依据。

### 2.2 产品指标

- 扫描结果入池转化率：扫描结果中被加入选股池的比例。
- 候选复盘完成率：入池标的在 T+1/T+5 内完成复盘的比例。
- 策略有效样本数：每个策略每周完成验证的标的数量。
- 回测使用率：策略页回测功能每周被使用的次数。
- 高风险误用率：mock/fallback 数据产生的候选被直接入池或用于结论的比例，目标持续下降。
- 任务失败可定位率：失败任务能看到失败分类、日志线索和下一步动作的比例。

## 3. 用户角色

### 3.1 策略研究员

关注策略逻辑、扫描结果解释、回测指标、复盘归因。需要快速判断候选是否值得跟踪。

### 3.2 交易复盘用户

关注每日候选、K 线走势、成交反馈、收益回撤和最终结论。需要高效完成状态流转和备注。

### 3.3 管理员

关注用户、租户、权限、审计、任务和系统健康。需要知道谁做了什么、系统是否可靠。

### 3.4 只读观察者

只能查看扫描、候选和报表，不允许创建任务或修改复盘结果。需要明确看到禁用原因。

## 4. 核心用户旅程

### 4.1 每日扫描到选股池

1. 用户进入今日工作台。
2. 查看行情源质量、任务告警和最近扫描。
3. 创建策略扫描任务。
4. 等待任务完成或自动轮询刷新。
5. 在扫描结果表查看评分、置信度、风险等级、行情源和入选理由。
6. 对候选执行加入选股池、查看 K 线、运行回测。
7. 系统记录来源、策略、解释、风险和数据质量。

### 4.2 选股池到复盘

1. 用户进入选股池。
2. 按日期、策略、风险、状态筛选候选。
3. 查看候选详情、K 线和扫描解释。
4. 更新状态：待复盘、观察中、已验证、已淘汰。
5. 填写复盘结论、成交反馈、收益、风险备注。
6. 系统沉淀复盘时间线。

### 4.3 策略验证到报表

1. 用户进入策略页。
2. 选择策略和回测参数。
3. 查看胜率、收益、最大回撤、夏普、盈亏比和交易样本。
4. 系统生成解释结论和风险标签。
5. 用户将结果用于策略调参或策略停用建议。
6. 周/月报表按策略聚合表现。

## 5. 功能需求

### 5.1 今日工作台

必须提供：

- API 健康状态。
- 行情源、数据质量、fallback 状态。
- 策略数量、扫描任务数量、选股池候选数量。
- 最近任务列表，展示状态、耗时、失败原因。
- 快捷入口：创建扫描、查看选股池、运行回测、同步行情。

验收标准：

- mock 或 fallback 行情必须出现明显警示。
- 任务失败数大于 0 时必须在首页可见。
- 用户不需要进入运维页即可知道今天是否适合继续扫描。

### 5.2 策略扫描

必须提供：

- 策略选择。
- 样本范围选择。
- 创建扫描任务。
- 自动轮询或手动刷新结果。
- 结果表：代码、名称、评分、置信度、风险等级、行情源、入选理由。
- 操作：加入选股池、查看 K 线、运行回测。
- 开发详情折叠展示。

验收标准：

- 扫描结果不再以 JSON 作为主界面。
- `data_quality=mock` 时不可隐藏警示。
- 加入选股池成功后给出明确反馈。

### 5.3 选股池

必须提供：

- 人工录入候选。
- 从扫描结果入池。
- 候选列表和分页。
- 筛选：日期、策略、状态、风险等级、来源。
- 状态流转：待复盘、观察中、已验证、已淘汰。
- 复盘字段：人工评分、复盘结论、成交状态、收益、风险备注。
- 复盘时间线。

验收标准：

- 同一日期、同一股票、同一来源重复入池时应去重或更新。
- 每条候选能追溯来源策略和入池原因。
- 用户能在 30 秒内完成一条候选的复盘状态更新。

### 5.4 K 线与标的详情

必须提供：

- 从扫描结果和选股池跳转到指定股票。
- 展示基础行情摘要：最新价、涨跌幅、成交量、MA5/MA20/MA25。
- 标记策略信号、入池日期、复盘节点。
- 展示该股票历史入池和复盘记录。

验收标准：

- 从候选表点击 K 线后必须带入股票代码。
- K 线页能说明当前数据来源和更新时间。

### 5.5 策略回测

必须提供：

- 回测参数：日期区间、持有天数、每日最大持仓、交易明细上限。
- 指标：交易次数、胜率、累计收益、最大回撤、夏普、盈亏比。
- 收益曲线。
- 交易样本表。
- 解释结论：风险等级、置信度、行动建议、假设条件。
- 历史回测记录。

后续增强：

- 基准对比。
- 手续费和滑点。
- 涨跌停成交约束。
- 参数寻优。
- 分市场环境归因。

验收标准：

- 无效日期和非法参数必须返回明确错误。
- 样本过少时必须降低置信度并提示风险。
- 回测结果不得被描述为投资建议。

### 5.6 报表中心

必须提供：

- 周报和月报。
- 按策略统计入池数、验证数、胜率、平均收益、最大回撤、高风险占比。
- 按来源统计扫描入池转化率。
- 导出 CSV 或 JSON。

验收标准：

- 报表数据必须能追溯到选股池和复盘记录。
- 报表中 mock/fallback 数据必须独立标记或排除。

### 5.7 权限与审计

必须提供：

- admin、editor、viewer 三类角色。
- viewer 禁止创建扫描、入池、复盘和回测写操作。
- 关键动作写入审计：扫描创建、入池、复盘更新、回测创建、用户管理。
- 敏感字段脱敏。

验收标准：

- 无权限按钮可以显示，但必须禁用并说明原因。
- 审计记录能按用户、租户、动作、时间查询。

### 5.8 生产监控

必须提供：

- 服务健康。
- 行情源健康。
- 任务列表、状态、耗时、失败分类。
- 日志摘要。
- 失败任务重试或取消。

验收标准：

- 任务失败后用户能看到失败分类和定位线索。
- stale running 任务能被识别。

## 6. 非功能需求

### 6.1 性能

- 首页首屏 API 聚合响应目标小于 1.5 秒。
- 任务列表、扫描列表、选股池列表必须分页。
- 长任务必须异步化，不阻塞请求。

### 6.2 可靠性

- 生产环境禁止静默使用 mock 行情。
- fallback 必须记录 provider chain 和错误原因。
- 启动入口不得写源码文件。
- 容器构建使用锁文件安装依赖。

### 6.3 安全

- API 写操作必须校验 CSRF。
- 所有租户数据必须校验 `X-Tenant-ID` 和用户绑定关系。
- 审计日志必须脱敏密码、token、cookie、api key。

### 6.4 可维护性

- 新能力只进入 React + `/api/v1`。
- legacy Jinja 和旧 `/api` 只保留兼容，不新增主功能。
- 前端页面需要统一中文文案，逐步修复 mojibake。

## 7. 当前版本范围

### 已完成基础

- React/Vite 前端。
- `/api/v1` 分层。
- 多租户和权限基础。
- 行情 provider 和 fallback。
- 任务队列和监控。
- 扫描解释字段。
- 策略回测 API。
- 选股池 v1 基础读写。

### 下一版本必须完成

- 扫描自动轮询。
- 扫描结果指定 K 线跳转。
- 选股池状态流转和复盘字段。
- 周报/月报最小可用版本。
- Python 测试环境修复和完整回归。

## 8. 风险与约束

- 当前仓库有大量缓存、依赖和运行数据改动，需要先收敛仓库卫生。
- Python 本地环境缺依赖，后端回归暂不可用。
- 新旧架构并存，短期内存在双轨数据风险。
- 行情源稳定性和可用性直接影响策略可信度。

## 9. 不做范围

短期不做：

- 实盘自动交易。
- 复杂组合管理。
- 高频行情。
- 完整新闻 NLP。
- 多市场跨资产支持。

这些能力需要等主流程、数据质量和回归体系稳定后再评估。
