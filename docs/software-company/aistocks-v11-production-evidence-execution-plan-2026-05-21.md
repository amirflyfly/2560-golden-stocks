# AiStocks v1.1 Production Evidence Execution Plan

## 1. 目标

上线前采集生产证据，证明 AiStocks v1.1 发布链路具备可验证性。执行完成后，应能够用 API 响应、页面截图、运行日志、数据库记录与外部推送 delivery 记录证明以下闭环真实可用：

- 生产服务健康状态可被检查。
- 授权用户可以登录并访问核心页面。
- 市场数据同步链路可触发、可追踪、可验证。
- 策略扫描可生成可执行信号。
- 纸面交易 `apply-signal` 可基于扫描信号创建模拟交易记录。
- `evaluate-exits` 可执行退出评估。
- 日报推送可触发并产生 delivery 记录。
- 外部推送通道可查询到发送结果与失败原因。

## 2. 前置条件

### 2.1 环境变量

确认生产或准生产环境已显式配置并记录以下环境变量：

- `APP_ENV=production` 或约定的准生产环境标识。
- `APP_DEBUG=0`。
- `SECRET_KEY` 使用强随机值，禁止使用开发默认值。
- `DATABASE_URL` 指向已授权的生产或准生产 MySQL 实例。
- `REDIS_URL` 指向可用 Redis 实例。
- `CACHE_BACKEND=redis`。
- `TASK_QUEUE_BACKEND=redis`。
- `TASK_EXECUTION_MODE=worker` 或发布方案要求的生产执行模式。
- `MARKET_DATA_PROVIDER` 与 `MARKET_DATA_FALLBACKS` 指向正式市场数据源及允许的备用源。
- 外部推送通道所需的 webhook、token、secret 等变量已按通道要求配置。

### 2.2 后端服务

- 后端服务已部署到目标环境，进程可被服务管理器或容器编排平台监管。
- API 入口域名、端口、反向代理与 TLS 配置已生效。
- 后端日志已接入可查询系统，至少能按时间、请求路径、状态码与 request id 检索。
- 任务队列 worker 已启动，能够处理市场数据同步、扫描、退出评估与推送任务。

### 2.3 前端构建/部署

- 前端已完成生产构建。
- 静态资源已部署到目标环境，并与后端 API 地址匹配。
- 浏览器可访问登录页、仪表盘、策略扫描、纸面交易、日报或推送相关页面。
- 已准备截图工具或浏览器录屏工具，用于保存关键操作证据。

### 2.4 数据库迁移

- 已完成数据库 schema migration。
- 已执行迁移后校验，确认核心表存在：用户、租户、市场数据、扫描任务、扫描结果、交易信号、纸面订单、纸面持仓、任务、外部推送 delivery。
- 已确认迁移脚本不可重复执行风险，必要时已有备份与回滚方案。

### 2.5 外部推送通道

- 至少配置一个可用于验证的外部推送通道。
- 通道目标应为测试群、测试 webhook 或准生产接收端，避免误发正式客户。
- 已确认推送接收端可查看消息内容与到达时间。
- 已确认系统可查询推送 delivery 状态、响应码、错误信息与重试记录。

### 2.6 测试账号

- 已准备具备管理员或发布验证权限的测试账号。
- 测试账号绑定有效租户，具备以下权限：
  - 登录系统。
  - 查看健康状态与任务状态。
  - 触发市场数据同步。
  - 创建策略扫描。
  - 查看扫描结果。
  - 执行纸面交易 `apply-signal`。
  - 执行 `evaluate-exits`。
  - 触发日报推送。
  - 查询外部推送 delivery。
- 测试账号密码、MFA 或访问控制策略已由执行人安全持有。

## 3. 执行步骤

### 3.1 健康检查

1. 请求后端健康检查接口，例如：
   - `GET /health`
   - `GET /api/v1/health`
   - `GET /api/v1/readiness`
2. 确认响应状态码为 200。
3. 确认响应内容包含服务状态、版本或依赖状态。
4. 保存 API 响应、请求时间、目标环境与后端日志片段。

### 3.2 登录

1. 使用测试账号访问生产或准生产登录页。
2. 提交登录表单。
3. 确认登录成功后进入应用首页或仪表盘。
4. 调用或观察 `GET /api/v1/me` 响应，确认当前用户、租户与角色正确。
5. 保存登录后页面截图、`/api/v1/me` 响应与相关访问日志。

### 3.3 市场数据同步

1. 进入市场数据或任务页面。
2. 触发市场数据同步接口，例如：`POST /api/v1/market-data/sync`。
3. 记录返回的 task id。
4. 查询任务状态，直到任务进入 `completed`、`failed` 或超时状态。
5. 查询市场数据覆盖率、快照或同步状态接口，确认数据源、证券类型、周期与数据质量。
6. 保存同步 API 响应、任务状态响应、页面截图、后端日志与数据库记录。

### 3.4 扫描

1. 进入策略扫描页面。
2. 创建一次策略扫描，例如使用 2560 策略、股票标的、日线周期。
3. 记录扫描任务 id。
4. 查询扫描任务与扫描结果接口，例如：
   - `POST /api/v1/scans`
   - `GET /api/v1/scans/{scan_id}`
   - `GET /api/v1/scans/{scan_id}/results`
5. 确认扫描任务完成，且结果包含可解释字段、市场数据质量字段与策略 runner 信息。
6. 若结果包含可执行 BUY 信号，记录该信号 id 或完整响应片段。
7. 保存扫描页面截图、API 响应、任务日志与数据库记录。

### 3.5 纸面交易 apply-signal

1. 从扫描结果中选择一个可执行信号。
2. 调用纸面交易接口，例如：`POST /api/v1/trading/paper/apply-signal`。
3. 确认响应状态码为 200 或发布标准定义的成功状态码。
4. 确认响应中包含订单、成交、持仓或信号关联信息。
5. 进入纸面交易页面，确认模拟买入结果可见。
6. 保存 apply-signal 请求体、响应体、页面截图、后端日志与纸面交易数据库记录。

### 3.6 evaluate-exits

1. 触发退出评估接口或任务，例如：`POST /api/v1/trading/paper/evaluate-exits`。
2. 记录返回任务 id 或评估结果 id。
3. 查询任务状态或评估结果。
4. 确认系统对已有纸面持仓执行了退出条件评估。
5. 若未触发退出，也需记录“无退出信号”的结构化响应。
6. 保存 API 响应、任务日志、页面截图与数据库记录。

### 3.7 日报推送

1. 进入日报、通知或推送页面。
2. 触发日报生成与推送流程。
3. 记录日报任务 id、推送通道 id 与 delivery id。
4. 确认接收端收到日报消息，或系统记录明确的发送结果。
5. 保存日报内容摘要、推送 API 响应、接收端截图、后端日志与 delivery 数据。

### 3.8 外部推送 delivery 查询

1. 查询外部推送 delivery 列表或详情接口。
2. 按日报任务 id、通道 id、时间范围或 delivery id 过滤。
3. 确认 delivery 记录包含：
   - 通道名称。
   - 请求时间。
   - 响应状态。
   - 响应码或错误码。
   - 重试次数。
   - payload 摘要或脱敏内容。
4. 保存 delivery 查询响应、数据库记录与推送接收端证据。

## 5. 回滚/止损

发现以下关键失败时，应立即停止发布推进并进入止损流程：

- 健康检查或 readiness 失败。
- 登录失败、权限异常或测试账号无法访问核心页面。
- 数据库 migration 后核心表缺失或出现不可恢复错误。
- 市场数据同步任务无法创建、持续失败或数据质量不满足发布门槛。
- 扫描任务无法完成，或扫描结果缺少策略、数据质量、解释性字段。
- `apply-signal` 无法基于可执行信号生成纸面交易记录。
- `evaluate-exits` 任务无法执行或导致交易数据异常。
- 日报推送无法触发，或 delivery 记录缺失。
- 外部推送误发正式客户、泄露敏感信息或出现不可接受的重试风暴。

止损动作：

1. 暂停发布窗口，不继续扩大流量或开放新用户。
2. 保留现场证据，冻结相关日志、任务 id、数据库记录与截图。
3. 通知发布负责人、后端负责人、前端负责人、运维负责人和业务验收人。
4. 若已切换流量，按发布预案回滚到上一稳定版本。
5. 若涉及数据写入异常，停止相关 worker 或禁用对应任务入口。
6. 若涉及外部推送异常，立即禁用相关推送通道或吊销测试 webhook。
7. 完成根因分析与修复验证后，重新安排证据采集。

## 6. GO/NO-GO 判定表

| 检查项 | GO 标准 | NO-GO 条件 | 结果 |
| --- | --- | --- | --- |
| 健康检查 | `/health`、`/api/v1/health`、`/api/v1/readiness` 均成功 | 任一关键健康接口失败或依赖不可用 | 待填写 |
| 登录与权限 | 测试账号可登录，租户与角色正确 | 登录失败、权限错误、租户绑定异常 | 待填写 |
| 市场数据同步 | 同步任务完成，数据质量字段可信 | 任务失败、数据缺失、数据源异常 | 待填写 |
| 策略扫描 | 扫描完成并产生可解释结果 | 扫描失败、结果结构不完整 | 待填写 |
| 纸面交易 apply-signal | 可执行信号成功生成纸面交易记录 | apply-signal 失败或未写入交易记录 | 待填写 |
| evaluate-exits | 退出评估可执行并返回结构化结果 | 任务失败、结果不可解释或数据异常 | 待填写 |
| 日报推送 | 日报任务完成，接收端可见 | 推送失败、内容错误或 delivery 缺失 | 待填写 |
| 外部推送 delivery | delivery 可查询且状态明确 | 无 delivery、状态不明或错误不可诊断 | 待填写 |
| 日志与数据库证据 | 日志、数据库记录可对应同一执行链路 | 证据无法关联或缺关键字段 | 待填写 |
| 回滚准备 | 回滚方案、负责人、触发条件明确 | 回滚路径不可执行或负责人缺失 | 待填写 |

最终判定：

- `GO`：所有关键检查项满足 GO 标准，证据完整可追溯，且无 P0/P1 未关闭问题。
- `NO-GO`：任一关键检查项触发 NO-GO 条件，或证据不足以证明发布链路可验证。
