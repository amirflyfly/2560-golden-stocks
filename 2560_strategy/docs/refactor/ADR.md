# 架构决策记录

## ADR-001：采用模块化单体作为重构目标

状态：已接受

背景：当前项目是 Flask 模块化单体，业务边界尚在演进。如果直接拆成微服务，会引入部署、事务和调试复杂度。

决策：先建立模块化单体，清晰划分 api、application、domain、infrastructure。

影响：降低重构风险，保留未来拆服务空间。

## ADR-002：多租户采用共享库共享表

状态：已接受

背景：系统需要多租户，但当前规模不适合一租户一库或一租户一 schema。

决策：MySQL 共享库共享表，业务表统一带 tenant_id。

影响：运维简单，但必须通过代码和测试严格防止串租户。

## ADR-003：行情数据源通过 Provider 抽象

状态：已接受

背景：当前行情能力主要依赖 AkShare，用户要求接入 mootdx。

决策：定义 MarketDataProvider，业务层只依赖抽象接口。mootdx、akshare、mock 均作为适配器。

影响：数据源可切换、可测试、可降级，避免第三方库污染业务代码。

## ADR-004：股票行情公共数据不按租户隔离

状态：已接受

背景：A 股基础行情是公共数据，按租户重复存储成本高。

决策：stocks、stock_daily_bars 为全局表；策略、扫描、选股、报告等用户业务数据按 tenant_id 隔离。

影响：节省存储，查询更简单；需要清晰区分公共数据和租户数据。
